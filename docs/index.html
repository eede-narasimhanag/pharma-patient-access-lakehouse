01 · Problem statement

How can disconnected operational feeds become a dependable analytics view?

Each source describes a different point in an access journey and has its own grain, status codes, and timing. Without explicit definitions and reconciliation, similar-looking counts can tell different stories.

The data challenge

Multiple systems, different meanings

A claim is a transaction, a HUB row is an event, a formulary row is an effective-dated plan-product interval, and a pharmacy row is a fill. Joining them carelessly can duplicate cases or hide reversals and unmatched records.

Rx claims Formulary HUB events SP fills
The project goal

Build a traceable, analytics-ready foundation

Create reusable transformations and clear metric definitions, preserve source-level facts, expose quality exceptions, and provide monthly views for reporting—without presenting synthetic results as real-world findings.

02 · Solution approach

A small lakehouse with clear contracts at every layer.

The local Python/SQLite pipeline is a fast test harness. Separate Databricks notebooks implement the same portfolio flow with Auto Loader, Delta tables, SQL, and a scheduled Job.

01

Ingest · Bronze

Load the four synthetic CSV feeds incrementally; preserve source values as strings with file and ingest metadata.

02

Standardize · Silver

Apply types and validations, deduplicate transaction IDs, and quarantine malformed rows rather than hiding them.

03

Model · Gold

Build payer, product, patient-token, and plan-product dimensions alongside transaction, event, and fill facts.

04

Measure · Serve

Create a one-row-per-case mart, monthly cohort metrics, quality checks, and dashboard datasets.

↳ Modeling decision: retain each source fact at its natural grain, then aggregate to a HUB case or enrollment-month / payer / product only where the metric requires it.

04 · Quality & metric rules

Make exceptions visible. Make definitions reviewable.

A dashboard is only as useful as its population, grain, and caveats. Checks persist outcomes and fail the run when a core pipeline invariant is broken.

Quality controls included

  • Source-to-target row reconciliation
  • Duplicate Rx transaction and malformed-row quarantine checks
  • Reversal matching and unmatched specialty-fill review
  • Typed date/status validation and referential checks

Example business definitions

  • Start within 30 days: first net-paid claim from enrollment through day 30, inclusive.
  • No-start rate (30d): enrolled cases without that start divided by all enrolled cases.
  • Dispensed case: at least one synthetic specialty-pharmacy fill.
Interpretation guardrail: “No start within 30 days” is a time-window metric, not proof of permanent abandonment. A review flag is an exception to investigate, not a silently discarded row.

Scope & responsible use

Fictional data. Transparent limitations.

This is a learning and portfolio project, not a production system or evidence of real patient outcomes. It does not claim regulatory compliance or represent any employer's systems.

  • All patients, products, payers, claims, and events are generated.
  • No real PII or PHI; synthetic tokens are used for joins.
  • Matching and cohort rules are simplified and documented.
  • The Databricks dashboard remains workspace-restricted; only its screenshots are shown here.
  • Metrics are illustrative, not validated commercial or clinical definitions.
